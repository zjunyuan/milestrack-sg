# CLAUDE.md

MilesTrack SG: a PWA that recommends which Singapore credit card to use per merchant category (MCC), tracks bonus caps per billing cycle, and keeps household miles vaults in Firebase Firestore. See README.md for user-facing features.

## Stack and running

- Vanilla ES modules, Tailwind (CDN), Firebase Auth (Google Sign-In) + Firestore. **No build step, no bundler, no package.json, no tests.**
- Run it by serving the repo root over HTTP (ES modules and the service worker won't load from `file://`), e.g. `python -m http.server 8000`, then open `http://localhost:8000`. Sign-in needs an email listed in `js/config.js`, and the origin must be an authorized domain in the Firebase project.
- The Firebase web config in `js/config.js` is a public client key, not a secret. Real access control lives in `docs/firestore.rules`.

## Layout

- `index.html`: app shell, views, datalists, modal sheets. Loads `js/app.js`.
- `js/config.js`: `APP_VERSION`, vault keys/labels, Firebase config, `ALL_MASTER_CARDS`, `MCC_DATABASE`, `CATEGORY_POOLS`, `DEFAULT_VAULT` (points→miles ratios), KrisFlyer tiers, yuu partner brands.
- `js/state.js`: single mutable `state` object shared by every module.
- `js/firebase.js`: auth, role resolution (email → vault key), Firestore listeners and CRUD.
- `js/recommender.js`: miles calculation per engine, single-swipe scorer, waterfall split solver, household MCC rules (`state.mccRules`). Shell pumps (MCC 5541, v1.63.7): UOB VS and UOB PPV (contactless) carry a 4% instant discount (`SHELL_PERK`; it does not need the S$1,000 spend, confirmed by the user). The ranking counts it as a tie-break at equal rate and as a mile-equivalent at `FCY_MILE_VALUE_CENTS` when comparing real miles, and orders VS ahead of PPV (the user's preference); local spend only.
- `js/mcc.js`: the one place that knows about every MCC. It combines `MCC_DATABASE` (hand-written rules), `MCC_NAMES` (labels only), and generated fallbacks.
- `js/mcc-names.js`: ~230 ISO 18245 codes with names and no card rules, plus `COMMONLY_EXCLUDED_MCCS`.
- `js/posting.js` / `js/posting-ui.js`: per-card transaction-date vs posting-date rules (source and date in the header), cycle-end maths, `countsTs(tx, card)` (the date a spend counts to; use it for cycle/cap membership instead of `tx.timestamp`), the month-end banner and the log-form hint. A transaction's optional `postTs` is the bank's posting date.
- `js/summary.js`: monthly summary block at the top of History (cap use per card entry, spend / share / miles / mpd per category with tap-to-filter, deltas vs last month; the yuu check counts partner merchants via `detectYuuMerchant`).
- `js/history-table.js`: desktop History table, filters (category, amount, trans/post dates), sort and totals; `state.txView` holds the view. When filters match nothing, the desktop table header (with its filter funnels) is still drawn (v1.63.12) and the empty state lists the active filters with its own Clear filters button (`activeFiltersHtml` / `clearAllTxFilters` in ui.js, v1.63.10).
- **Statement view** (`js/stmt-filter.js`, v1.63.20): `state.txView.stmt` = one statement checkpoint ({vk, cardId, from, to, label, bank, sure, maybe}); entries of that vault's cards (or the ledger card's family) whose posting date (else transaction date) is in (from, to] pass (`passesStmt` in passesView), the History month picker is ignored while it is on, and a banner shows, in the bank's points with miles beside them (v1.63.22), what the bank credited, the base points the app is sure of, the bonus that could land in that statement (for the previous statement's entries / for these entries) and a verdict (in range / short / more than expected) (`stmtBannerHtml`, from `expectedCredits`). Opened from "Show these entries →" on each statement check in Check with banks (capture-phase document listener in reconcile-ui.js, because modal sheets stop click bubbling), or chosen from the desktop Statement select (`#txStmt`, always shown; it lists statements once the card filter points at one vault and otherwise says "Filter to one card first", v1.63.30) / phone Statement chip. Cleared by ✕ on the banner, Clear filters, or moving the card filter to another vault. When the card filter is one card (or its channel entries) and the bank prints a row per card (DBS: Vantage, Woman's World, yuu in one summary), the Statement list and its checks use that card's own row (`periodsForFilter` in stmt-filter.js, v1.63.45); before this a Woman's World filter was checked against every DBS card's total. - The desktop History table has Base pts / Bonus pts columns (`pointsSplit(tx)` in reconcile.js: base from `BONUS_SPLIT`, else the card's `baseMpd`; a Base entry is all base; v1.63.23), totalled in the Total row; on narrow desktops `#txList` scrolls sideways. For HSBC only (v1.63.24; it prints "Points Earned" = base and "Points Adjusted" = the previous statement's bonus; UOB's adjusted is fee reversals and other items), the statement banner lines them up with the app's base for these entries and its bonus for the entries that posted in the previous statement only (v1.63.26: the window rule had also pulled in the bonus for the statement before that), with a difference per line and a still-to-come line for these entries' bonus. - Statement import (`statements.js` / `statement-import.js`): the statement wins over entries. `matchLines` matches on the chosen card's family, `matchOtherCards` finds entries logged on the wrong card, matched entries get `stmtConfirmed`, and unconfirmed entries in the statement's period (older than 7 days before its last line) are offered for removal. Several files can be picked at once (batch mode: `B.files`, per-file state `S` swapped with `withFile`, one shared `ctx` so overlapping files do not double up and one Undo reverses the lot). A PDF holding several cards (UOB prints one section per card) is split by `splitCardSections()` in `pdf-statement.js` (`readPdfParts`), and each section becomes its own batch entry matched by card name or remembered last 4 digits (every upload, even one card, is shown as that list: there is no top card dropdown, a row the app cannot match asks "Which card is this?"); UOB's first date column is the Post date. **Refunds** (v1.63.28): `matchRefunds` (statement-import.js) pairs a credit line (not a payment, rebate or cashback: `NOT_REFUND`) with the purchase it reverses (same amount, merchant words overlap, purchase up to 120 days before), preferring a line in the same file over an entry already in the app. That purchase is kept (spend still lines up with the statement) but saved with `refunded`, `refundTs`, a `stmtNote` and no miles or points; a purchase already in the app loses its points from the Vault (`vaultAdj`, so Undo gives them back). The review names the purchase under the credit, the counts say "N refunds matched", and History tags it Refunded (`rateTag`). The card a row starts on: the statement's own name decides; the card remembered for those last 4 digits wins only when the name agrees with it (same family) or names nothing (`suggestCardId`, v1.63.12; a wrong pick once saved, HSBC as OCBC, used to stick). Citi pages are named from their product line ("CITI REWARDS VISA SIGNATURE 4147 …", v1.63.9) so Visa, Mastercard and PremierMiles (`citi-pm`) are told apart. A file's sign convention is taken from its payment lines (a payment is a credit; only card-payment wording counts, `CARD_PAYMENT`, v1.63.47: "STARHUB EPAYMENT" and "REDMART SG PAYMENT" are purchases and once flipped a whole DBS section); a line in that wording is always read as a credit, whatever its sign, and an existing entry in that wording saved as spend is offered for removal on the next import even with a statement mark, v1.63.48 when it has any, else from the share of negative spend lines (`prepareCore`). A PDF with no text layer (HSBC draws its letters as shapes) is read by text recognition: Tesseract.js is loaded from a CDN on demand, up to three readings with different settings are combined (`readByOcr` / `combineOcr`), and the result is only accepted if previous balance + lines = the statement total (`verifyBalance`), otherwise the row shows an error and nothing can be imported. A DBS consolidated PDF ("DBS YUU VISA CARD NO.: 4119 …", one section per card, one date per line, no year: it comes from "STATEMENT PRINTED ON") is split by the same function; each section's previous balance + lines must equal its printed `TOTAL:` (`verifySection`) or that card is shown as an error and not imported. A card with no lines is kept only as an "unused card" part (`looksUnused`, `statementYm` in `pdf-statement.js`; v1.63.8): nothing to import, but its statement month is ticked in the coverage grid (`F.emptyYm`, `coverageFor` writes `{n: 0}`), only for cards the app knows and, for DBS, only if previous balance = the printed `TOTAL:`. OCBC PDFs print one date as day/month in numbers ("11/06") and credits in brackets ("(1,641.00 )"): `pdfTextToRows` reads them with `numRe`, the statement date comes from "25-06-2026" under STATEMENT DATE, and `looksUnused` accepts numeric dates and ignores payment lines (v1.63.40; before this every OCBC PDF looked like an unused card and nothing imported). OCBC files carry only the posting date: `POSTING_ONLY_CARDS` in `statements.js` makes `matchLines`/`matchOtherCards` accept a 0 to 3 day lag, keep the entry's own transaction date and record the file date as `postTs`. `state.stmtCoverage` (settings doc, merged) records card-months imported and feeds the coverage grid. Since v1.63.11: Citi lines take their year from the month before the "Payment Due Date" (pages print no statement date; before this a January statement's December lines became December of the current year and ticked the whole year); `coverageFor` never ticks a month after the statement's own month (`stmtYm` on each PDF part) or after the current month; the months an import ticked for the first time are kept in localStorage `milestrack_last_cover` and Undo takes them back (`untickCoverage`, saved whole with `replaceCoverage` in firebase.js, `mergeFields` because a merge cannot remove months); tapping a card's name in the Upload sheet's grid clears that row, and "Clear all ticks" under it clears every row (v1.63.13).
- `js/fcy.js`: overseas "after FX fees" maths, pure helpers: `billedAmount` (miles are earned on spend + FX fee), `fcyEconomics` (fee, cost per mile = fee ÷ miles, net at `FCY_MILE_VALUE_CENTS` = 1.3¢), `incremental` (cost per extra mile and gain vs a baseline) and `planOverseas`. ## Domain model (config.js)

- **Card** (`ALL_MASTER_CARDS`): one physical card can appear as several entries, one per earning channel (e.g. `uob-ppv-contactless` / `uob-ppv-online`, `uob-vs-contactless` / `uob-vs-fcy`, `uob-ls-dining` / `uob-ls-travel`). Key fields:
  - `engine`: how miles round. `uob-5` / `ocbc-5` use S$5 blocks, `dbs-5` is DBS, `citi-1` is per dollar, `yuu-10` is special.
  - `cycleType`: `calendar` | `statement` (needs `cutoffDay`) | `uncapped`. `monthlyCap: 999999` means effectively uncapped.
  - `channelMode`: `inperson` | `online` | `both`. `isContactlessOnly`, `minSpend`, `bonusMpd`, `baseMpd`, `vaultKey` (→ `DEFAULT_VAULT`).
  - `fcyFee` (% on foreign-currency spend, including the 1% Visa/Mastercard fee) and `fcyFeeSource` (where it came from, official vs secondary, and the date checked). Used by `js/fcy.js` and the Overseas ranking. Also `fcyMpd` (top-tier overseas mpd on ordinary spend, used for uncapped fallback cards and "At max rate"), optional `fcyEarnsOnFee` (overrides `FCY_EARN_ON_FEE` in config.js, default true: miles accrue on the fee too) and `FCY_MILE_VALUE_CENTS`. To react to a bank changing its fee or rate, edit these in config.js only. Re-check against the bank's own pages when a bank changes its fee.
- **MCC rules** (`MCC_DATABASE`): `{ name, notes (HTML), candidatesLocal: [{id, baseRate}], candidatesOverseas: [...] }`. Empty lists mean excluded. Adding an entry overrides the generated fallback for that code. Every `id` must exist in `ALL_MASTER_CARDS`.
- **Precedence**: an active household rule (Firestore `milestrack_mccRules`, primary-only write, optional expiry) replaces the `MCC_DATABASE` entry. Next comes `MCC_DATABASE`, then the generated fallback from `mcc.js` (base-rate uncapped cards, or a "commonly excluded" result).
- **Citi Rewards Visa** (`citi-rewards-visa`, v1.58.0): a second Citi card beside the Mastercard (`citi-rewards`, shown as "Citi Rewards Mastercard"). Same rules, own vault `citi_typ_visa` (v1.63.15: Citi keeps a separate ThankYou balance per card; the Mastercard stays on `citi_typ`, "Citi TYP Mastercard"; fold it back into `citi_typ` when the Visa closes), own S$1,000 cap, `cutoffDay` 29 (setting `cutoffDays.citiVisa`, input `citiVisaCutoff`), card art `citi-rewards-visa.png` (v1.62.2; the real Visa Signature card, cardholder name painted out because the repo is public). Every `citi-rewards` special case (cardrules, posting, Kris+ and in-store filters in recommender, OCBC promo lists, `MCC_DATABASE` candidate lists, category pool) needs the Visa id too.
- **OCBC merchant whitelist** (v1.63.42): OCBC Rewards pays the bonus by merchant name, whatever the MCC (T&C 5 Oct 2026 section c: Alibaba, AliExpress, Amazon, Ezbuy, Guardian, Lazada, Mustafa, NTUC Unity, Shopee, Taobao, TikTok Shop, Watsons; not Shopee Pay, not MCC 5411). `ocbcMerchantRate(text, ts, mcc)` in cardrules.js gives 4, or 6 for Watsons/Shopee/Lazada/Taobao/TikTok during the promo (1 Jul 2025 - 31 Mar 2027, extended once), and is used by statement import (`estimateTx`) and the bonus finder. OCBC awards per S$5 block: base 5, regular bonus 45, promo bonus 25 OCBC$ per S$5 (checked: Taobao S$9.27 = 75 OCBC$, bonus 70 on the next statement). Caps are counted in S$5 blocks a month (v1.63.44, `estimateTx`): 45 regular bonus on the first 222 blocks (S$1,110), 25 promo bonus on the first 200 (S$1,000); a month that went over both paid exactly 9,990 + 5,000. For other cards a line that crosses the cap earns the bonus on the part that fits and base on the rest (it used to go to base whole), and only bonus spend (`capSpend`, and existing entries not on Base or refunded) fills the cap.
- **Bank-rule cards**: `js/cardrules.js` generates candidates for UOB VS/PPV (contactless and online), OCBC Rewards, Citi Rewards, HSBC Revolution, DBS WWMC and Maybank Horizon air tickets from each bank's exclusion/eligibility list, overriding their hand-written `MCC_DATABASE` entries. Sources and dates are in its header.
- **Locked rate**: a card's `lockedMpd` (DBS yuu 2.78 mpd at partner merchants) is what it earns while its minimum-spend condition is unmet; `minSpendGate()` returns it as `lockedMpd` (falls back to `baseMpd`) and the recommender uses it for "now" miles and the unlock note.
- **Dated rates**: a card's `rateSchedule` (applied by `applyRateSchedule()` in config.js) switches `baseMpd`/`bonusMpd` on a date (DBS Vantage 1.4 from 2 Nov 2026).
- **Spend tiers**: a card's `tierRule` (KrisFlyer UOB S$1,000 SIA Group, Maybank World/Horizon S$800/S$4,000) drives the progress display in `js/tiers.js`.
- Still hard-coded in recommender logic: the OCBC 6 mpd S$1,000 cap, the yuu S$800 + 4-merchant rule, and the Maybank World FCY tier thresholds (S$800 / S$4,000) in the recommender.
- Every `mcc` in `retailers.js` must be a known code (`MCC_DATABASE` or `MCC_NAMES`).

## Firestore

Collections: `milestrack_vaults` (doc per vault key), `milestrack_txns` (`owner` = vault key), `milestrack_points` (`owner` = vault key; v1.59.0 points check: statement summaries, typed balances, transfers/redemptions), `milestrack_settings` (doc per vault key), `milestrack_merchants` (shared brand corrections), `milestrack_mccRules` (shared per-MCC household rules), `milestrack_config` (document `roles`: who is which role; read by members only, no app writes).

- Vault key `primary` is shown as "Household". Keep the ID; existing data depends on it.
- Client-side role checks are UX only. Any new collection or field needs a matching change in `docs/firestore.rules`. Rules aren't deployed from the repo: the user pastes them into the Firebase console, so call that out when rules change.
- **Role email lists live only in Firestore** (v1.62.0, the repo is public): document `milestrack_config/roles` = `{primary, sister, member1, member2, test}` (each an array of lowercase emails) plus `labels` (`{primary: "...", sister: "...", ...}` display names), edited by hand in the Firebase console (rules deny writes). The repo only has neutral placeholders in `VAULT_LABELS`; `applyLabels` (firebase.js) fills the real ones after sign-in and caches them in localStorage `milestrack_labels_cache`. Vault IDs `member1` / `member2` are neutral on purpose (the repo is public); they were renamed in v1.62.1 when no data existed under the old IDs. `docs/firestore.rules` reads it with `get()`; `resolveVaultKey` (async, firebase.js) reads it after sign-in, treats a permission refusal as guest, and falls back to the last role seen on the device (localStorage `milestrack_role_cache`) when offline. **Order matters when rules change: create/keep the document first, then publish the rules, then deploy the app.** Adding a role also touches `ALL_VAULT_KEYS`, `VAULT_LABELS`, role resolution in `firebase.js`, `state.userRole` comments, and `canAccess()` in the rules.

## Releasing a version

Bump the version together in all of these, or clients keep serving stale cached files:

1. `js/config.js` → `APP_VERSION`
2. `sw.js` → `CACHE_NAME` (`milestrack-cache-vX.Y.Z`)
3. `index.html` → `js/app.js?v=X.Y.Z` and `css/style.css?v=X.Y.Z` (the stylesheet link has no other cache-buster, so a stale copy can survive an update)
4. `docs/firestore.rules` header comment (when the rules changed)

New JS modules or card images must also be added to `CORE_ASSETS` / `CARD_ASSETS` in `sw.js`.

Commit messages follow `vX.Y.Z: short summary`.

## Conventions

- Keep it buildless: plain ES module imports with relative `./x.js` paths, no npm dependencies.
- Shared state goes through `state` in `js/state.js`. Firestore writes update `state` optimistically and roll back on failure (see the `mccRules` save/remove in `recommender.js`).
- Escape user or Firestore-sourced strings with `escapeHtml` (from `retailers.js`) before putting them in `innerHTML`. `MCC_DATABASE.notes` is trusted HTML.
- UI copy is plain English with emoji markers (⚠️ exclusions, ❌ excluded, 🏠 household rule). Monetary values are S$.
- Card rates and bank T&Cs change often. When editing rates, update the card's `hint`, the relevant `MCC_DATABASE` notes, and the README together.
